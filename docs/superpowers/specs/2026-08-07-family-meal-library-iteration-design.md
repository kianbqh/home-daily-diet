# 家庭点菜与菜品库迭代设计

## 目标

补齐“今天吃什么”的可用闭环，并让已有菜品页面成为菜品管理入口：家庭成员可以提交想吃的菜，进入已有菜品页面进行简短评价，菜品可以被安全删除，邀请链接不会把已经属于当前家庭的人再次引导加入。

## 范围

本轮包含：

- 点菜流程的页面可用性和状态展示
- 已有菜品页面的简短评价
- 记录菜品页面的版式整理
- 菜品软删除和删除确认
- 邀请链接的当前家庭判断

本轮不包含：

- 聊天功能
- 详细制作步骤、语音解析或大语言模型
- 记录菜品首次录入页中的评价和备注表单
- 永久物理删除历史制作记录

## 方案

### 点菜

沿用现有 `mealSessions` 和 `mealSubmissions` 数据模型。首页进入当天晚餐页面时确保当天只有一个选餐会话；菜品卡片点击一次提交当前成员的想吃选择，再点一次取消。页面显示每道菜的提交人数，并允许从已提交菜品中选择最终菜单。确认后会话锁定，已确认页面提供继续记录制作记录的入口。

页面层补充空状态、会话初始化和提交后的刷新保护，确保没有菜品时先引导录入，已有菜品时能稳定进入点菜页。

### 简短评价

评价放在已有菜品页面，也就是 `pages/dish-edit/dish-edit` 在 `isExisting && !isEditingProfile` 状态下展示的菜品详情区域；首次记录菜品和编辑菜品资料时不展示评价板块。

评价只有三个选项：`like`（喜欢）、`neutral`（一般）、`dislike`（不太喜欢）。评价按“菜品 + 当前家庭成员”保存并覆盖该成员上一次评价，不创建重复的制作记录。菜品汇总继续提供家庭整体评价统计，并兼容已有制作记录中的历史 `rating` 字段。

共享状态新增 `dishRatings` 数组，每条记录包含 `familyId`、`dishId`、`memberId`、`rating`、`updatedAt`，文档键使用 `dishId|memberId` 保证幂等。云端和本地合并时按该键保留较新的记录。

### 菜品页面布局

将现有记录页整理为三个清晰区域：

1. 顶部菜品信息卡：菜名、封面或统一无图占位、历史记录次数。
2. 本次记录卡：本次照片、日期、餐次和可选标签。
3. 已有菜品操作区：简短评价、编辑菜品、删除菜品。

评价只出现在已有菜品详情状态；首次录入页面保持简洁，不恢复之前明确移除的“吃起来怎么样”和“备注”输入。

### 删除菜品

采用软删除而不是从数组中物理移除：菜品增加 `status` 和 `deletedAt`，删除后状态为 `deleted`。菜品库、点菜页、相似菜名检查和首页最近菜品只读取 active 菜品；历史 `cookingRecords` 保留，避免云端合并时被另一台设备重新恢复。

已有菜品页面提供“删除这道菜”按钮，点击后弹出确认框；确认后返回菜品库并显示删除成功提示。删除后的菜品不再允许追加制作记录。

### 邀请链接

家庭页收到 `inviteCode` 时先检查当前家庭的有效邀请码。若邀请码与当前家庭一致，清除待处理邀请并直接显示家庭页面；只有邀请码属于其他家庭时才显示加入确认。检查失败或当前仍未完成云端同步时保留现有加入流程和明确错误提示。

## 错误处理

- 点菜提交失败时保留当前页面并显示“暂时无法提交选择”，不清空已显示选择。
- 评价失败时保留当前选择，并提示“评价未保存”。
- 删除失败时不返回上一页，提示“菜品删除失败”。
- 已删除菜品通过旧链接打开时显示不可用状态，不允许继续记录。
- 邀请码失效、撤销或不属于当前家庭时继续使用现有邀请码错误文案。

## 验证

- domain 测试：点菜提交/取消/确认、评价幂等、删除后过滤、历史记录保留。
- view-model 测试：活跃菜品过滤、评价统计、已删除菜品不可进入点菜结果。
- page 测试：点菜页面初始化和提交、菜品详情评价与删除、当前家庭邀请链接不再弹加入提示。
- 静态模板测试：首次记录页没有评价/备注输入，已有菜品页包含评价和删除入口。
- 运行现有全量测试、JS 语法检查和 `scripts/smoke-check.js`。
