# 制作记录评价、标签与回收站迭代设计

## 目标

在现有“今天想吃啥”小程序中补齐以下能力：

1. 评价准确归属到某一次制作记录，并支持半星和文字评价。
2. 菜品详情页展示该菜品的综合评分、星级分布和家庭成员评价，同时保留每条评价对应的制作记录。
3. 重做制作记录展示，使照片、日期、餐次、记录人和评价关系清晰。
4. 将菜品标签改为预设标签点击选择，添加菜品时可不选，详情页可补充或修改。
5. 修复追加制作记录时照片状态残留的问题，明确区分菜品封面与本次制作照片。
6. 增加回收站，软删除后的菜品可以查看历史记录，也可以恢复或彻底删除。

## 范围

### 本轮包含

- 制作记录级评价：半星评分、可选文字、成员身份和编辑。
- 菜品详情页的综合评分与底部“家人评价”区域。
- 制作记录时间线卡片和无图统一占位。
- 预设菜品分类与特点标签，添加页和详情编辑页均可点击选择。
- 追加记录照片上传状态清理。
- 回收站、恢复、彻底删除和删除后的云端防恢复。
- 本地状态、CloudBase 同步、云函数状态合并和相关测试。

### 本轮不包含

- 评价回复、点赞、聊天或通知。
- 评价图片上传；制作照片仍属于制作记录。
- 复杂的角色权限；家庭成员默认可以查看全部评价，只能修改自己的评价。
- 对 CloudBase 历史事件日志做物理清理；彻底删除指从当前家庭状态和应用可访问数据中移除，并使用墓碑阻止旧设备恢复。

## 设计决策

### 1. 评价数据模型

制作记录继续独立保存照片和制作信息：

```text
cookingRecords[]
- id
- familyId
- dishId
- recordedBy
- recordedAt
- mealType
- image
```

新增家庭状态数组 `recordReviews`：

```text
recordReviews[]
- id: `${recordId}|${memberId}`
- familyId
- dishId
- recordId
- memberId
- stars: 0.5 - 5
- text: string
- createdAt
- updatedAt
```

约束：

- `stars` 只能是 `0.5` 的倍数，范围为 `0.5` 到 `5`。
- `text` 可为空，建议限制为 300 个字符以内。
- 同一家庭成员对同一制作记录最多一条评价，重复提交覆盖自己的评价。
- 评价展示使用成员称呼和评价时间；不展示 openid 或内部家庭 ID。
- 新版本不再写入菜品级 `dishRatings`，也不在首次记录表单中出现评价或备注字段。

旧数据兼容：

- 保留旧版 `dishRatings` 和 `cookingRecords.rating/note` 字段，避免读取旧云端状态时报错。
- 旧版菜品级评价没有 `recordId`，不得擅自归到某一次制作记录；它们只作为“历史评价”参与菜品汇总，直到产生新的制作记录级评价。
- 新增和编辑评价全部使用 `recordReviews`。

### 2. 菜品详情页展示

详情页从 `cookingRecords`、`recordReviews` 和 `members` 做视图模型拼接，不额外保存容易过期的菜品汇总字段。

页面结构：

1. 顶部菜品卡：菜名、封面、制作次数、综合平均分、评价数量。
2. 星级分布：显示 1 到 5 星数量；平均分支持半星展示。
3. 制作记录时间线：每张卡显示制作日期、餐次、记录人、照片、评价数量。
4. 每张记录卡提供“评价这次制作”，打开该记录的半星选择和文字输入。
5. 页面底部“家人评价”：按最新评价排序，每条评价显示成员、星级、文字，并显示“对应：日期 + 餐次”以及小尺寸制作照片。

评价保存后同时更新对应记录的评价数量、页面底部评价列表和顶部综合评分。删除的菜品从回收站打开时仍可查看这些历史内容，但不可追加制作记录或新增评价。

### 3. 半星选择交互

评分控件使用 10 个半星点击区域表示 `0.5` 到 `5`：

- 左半区域选择半星，右半区域选择整星。
- 未选择时显示提示“选择本次制作的味道评分”。
- 编辑已有评价时回填原星级和文字。
- 保存按钮在星级为空时提示先选择评分；文字可以为空。

### 4. 制作记录版式

将已有菜品页的历史记录改为时间线卡片：

- 卡片顶部是日期、餐次和记录人。
- 中间优先展示制作照片；没有照片时使用统一的渐变首字占位，不显示空白大块。
- 底部展示“x 条评价”或“暂无评价”，并提供评价入口。
- 多条记录用细线和日期顺序连接，最新记录在前。
- 记录详情和评价汇总保持同一页面，不要求用户在多个页面之间来回寻找。

首次记录页仍保持简洁，只负责菜名、照片、日期、餐次和标签；评价发生在记录保存之后的菜品详情页。

### 5. 标签模型与选择器

菜品增加可选的 `category` 字段，现有 `tags` 字段继续用于特点标签：

```text
dish
- category: 荤菜 | 素菜 | 汤 | 主食 | 其他 | ''
- tags: string[]
```

分类单选：

- 荤菜
- 素菜
- 汤
- 主食
- 其他

特点多选：

- 家常
- 快手
- 下饭
- 清淡
- 辣味
- 早餐
- 节日菜

添加菜品和编辑菜品资料均使用点击标签，分类和特点都不是必填。菜品库筛选支持分类和特点；已有旧文字标签如果能匹配预设值则映射到对应选项，无法匹配的旧值保留在数据中但不再提供手动输入入口。

### 6. 照片状态分离与清理

页面状态明确拆分：

- `dishCover`：菜品长期封面，只在编辑菜品资料时使用。
- `recordImage`：当前正在追加的制作记录照片。

保存流程：

1. 用户选择照片后只更新 `recordImage`。
2. 保存时先上传 `recordImage`，上传失败则不提交这条制作记录，并保留照片供用户重试。
3. `addCookingRecord` 成功后，将 `recordImage` 和显示预览立即清空。
4. 再次进入“追加这次记录”时，默认显示空的本次照片区域，不复用上次记录照片。

### 7. 回收站与彻底删除

菜品库增加“回收站”入口，新增回收站页面展示 `status === 'deleted'` 的菜品。每项显示菜名、封面、历史制作次数、评价数和删除时间，提供：

- **恢复菜品**：将状态恢复为 `active`，保留全部制作记录和评价。
- **彻底删除**：二次确认后执行不可逆清理。

彻底删除移除：

- 菜品本身；
- 该菜品全部 `cookingRecords`；
- 该菜品全部 `recordReviews` 和旧版评价；
- 未确认点菜提交中的该菜品；
- 已确认菜单中的该菜品 ID。

为了防止另一台设备用旧快照把已彻底删除的菜品重新合并回来，状态新增 `purgedDishes` 墓碑数组：

```text
purgedDishes[]
- dishId
- purgedAt
```

云端和本地合并时先合并墓碑，再过滤所有相关菜品、记录、评价和选餐引用。墓碑本身不包含菜名、照片或制作内容。回收站彻底删除后的菜品不能恢复。

## 云端同步

继续使用现有 `family_states`、`family_states_events` 和 `family-access` 云函数，不新增数据库集合：

- `recordReviews` 按 `recordId|memberId` 合并，保留较新的 `updatedAt`。
- `category` 和 `tags` 随菜品资料同步。
- `purgedDishes` 按 `dishId` 并集同步，墓碑优先于旧菜品数据。
- 云函数重放历史家庭事件时始终应用墓碑过滤，避免旧事件重新恢复已彻底删除内容。

## 错误处理

- 评价保存失败：保留表单内容，提示“评价未保存”，不更新本地评价列表。
- 星级非法、制作记录不存在或菜品已删除：拒绝保存并提示明确原因。
- 照片上传失败：不提交制作记录，保留本地照片供重试。
- 恢复或彻底删除失败：停留在回收站，显示失败提示。
- 彻底删除需要二次确认，并明确提示历史记录和评价不可恢复。

## 验证计划

- domain：半星校验、评价按记录和成员幂等、综合评分、标签选择、软删除、恢复、彻底删除和墓碑过滤。
- view-model：菜品详情的平均分/分布/评价列表、制作记录与评价关联、回收站列表。
- page：半星选择、评价文字保存、记录卡评价入口、标签点击、图片清空、回收站恢复和彻底删除确认。
- cloud sync：评价合并、标签合并、墓碑阻止旧设备恢复。
- static/smoke：首次记录页不包含评价输入，页面路由和上传包检查通过。
- 全量运行 `npm test`、语法检查、`scripts/smoke-check.js` 和 `git diff --check`。
