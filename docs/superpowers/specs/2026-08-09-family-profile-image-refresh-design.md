# 家庭资料、共享图片与下拉刷新设计

## 背景

当前家庭空间存在三类跨客户端不一致：成员修改昵称后其他家人仍看到“我”；家庭名称修改后其他家人仍看到默认名称；上传者能看到菜品图片，但其他家人无法稳定显示。与此同时，页面只刷新本地内存，没有统一的云端重新拉取入口。

排查确认了以下根因：

1. `family.name` 和 `members[].displayName` 没有 `updatedAt`。状态合并时，旧客户端的默认值会在时间相同或缺失时覆盖云端新值，并再次回写。
2. `App.onLaunch` 只触发一次云端 hydration，各页面 `onShow` 仅重建本地视图，因此另一台设备的新数据不会及时进入当前客户端。
3. 图片虽然以 `cloud://` 文件 ID 保存，但展示层直接在客户端调用 `getTempFileURL`。当云存储规则按上传者限制读取时，其他家庭成员无法换取可显示的 HTTPS 地址。
4. 当前 hydration 每次合并后都会回写云端；如果自动同步直接复用该行为，会产生大量没有业务变化的事件记录。

## 目标

- 昵称和家庭名称在任一成员修改后，其他成员进入页面、返回页面或下拉刷新即可看到新值。
- 家庭成员都能显示家庭内菜品及制作记录的云端图片。
- 首页、菜品库、菜品详情、点菜、家庭空间和回收站均支持顶部下拉刷新。
- 自动同步失败不打断使用；手动刷新失败给出明确提示，并始终结束刷新动画。
- 保留本地优先和离线可用能力，不引入实时数据库监听、角色权限或新的后端服务。

## 非目标

- 不实现秒级实时推送或 WebSocket 监听。
- 不拆分现有家庭聚合状态为多个全新业务集合。
- 不修改家庭角色模型，也不新增管理员权限。
- 不把临时 HTTPS 图片地址持久化到数据库。

## 方案选择

采用“字段版本化 + 统一同步入口 + 云函数授权解析图片”的组合方案。

只增加下拉刷新不能解决旧默认值反向覆盖；只调整云存储为公开读又会扩大图片访问范围。完整拆分家庭、成员和菜品集合则超出当前项目规模。选定方案在保留现有状态结构的同时修复合并语义，并把图片访问授权放回已经承担成员校验职责的 `family-access` 云函数。

## 数据模型与合并规则

### 家庭资料

`family` 增加 `updatedAt`：

```js
{
  id: 'family-xxx',
  name: '我们家',
  createdAt: '2026-08-09T00:00:00.000Z',
  updatedAt: '2026-08-09T00:00:00.000Z'
}
```

创建家庭时令 `updatedAt` 等于 `createdAt`；修改名称时写入当前时间。合并时比较 `updatedAt || createdAt`，较新者胜出；时间相同优先保留云端值，防止旧客户端默认值反向覆盖。

### 成员资料

成员增加 `updatedAt`：

```js
{
  id: 'member-xxx',
  displayName: '妈妈',
  joinedAt: '2026-08-09T00:00:00.000Z',
  updatedAt: '2026-08-09T00:00:00.000Z'
}
```

创建或加入家庭时令 `updatedAt` 等于 `joinedAt`；修改昵称时写入当前时间。合并时比较 `updatedAt || joinedAt`，时间相同优先云端值。

`currentMemberId` 继续只保存在设备本地，不进入共享状态，也不因其他客户端同步而改变。

### 旧数据迁移

加载旧状态时补齐缺失时间：家庭使用 `createdAt`，成员使用 `joinedAt`。不重新生成时间，避免迁移本身被误认为一次最新编辑。第一次真实修改会写入新的 `updatedAt`。

## 统一云端同步

Store 暴露统一的 `syncFromCloud({ force })`，并保留 `hydrateFromCloud()` 作为兼容别名。

- 同一时刻只允许一个拉取请求；并发页面复用同一个 Promise。
- 页面 `onShow` 调用非强制同步，五秒内已经成功同步过则直接使用本地状态。
- 下拉刷新调用 `force: true`，绕过五秒间隔。
- 合并结果始终保存到本地并通知订阅页面。
- 只有合并结果包含云端尚未拥有的本地变化时才回写；纯拉取不新增 `family_states_events` 记录。
- 同步失败时保留当前本地状态和现有错误状态，不清空页面。

六个页面使用同一刷新辅助函数：先同步 Store，再执行页面原有 `refresh()`。`onPullDownRefresh` 在 `finally` 中调用 `wx.stopPullDownRefresh()`，确保成功和失败都会结束动画。`app.json` 全局启用下拉刷新。

## 家庭图片访问

新增 `family-access` 动作 `resolveFiles`：

1. 客户端提交 `familyId` 和去重后的 `fileIds`，单次最多 50 个。
2. 云函数先用当前微信 `OPENID` 校验调用者是该家庭的有效成员。
3. 只接受路径位于 `family-meals/<familyId>/` 下的 `cloud://` 文件 ID；其他家庭或其他目录的文件返回拒绝。
4. 云函数通过服务端 CloudBase SDK 调用 `getTempFileURL`，返回 `{ fileID, tempFileURL }` 映射。
5. 客户端只在内存中缓存结果 30 分钟；数据库继续保存原始 `cloud://` 文件 ID。

CloudBase 服务端 SDK 正式支持批量 `getTempFileURL`，返回文件 ID 与 HTTPS 临时地址，适合由已经完成家庭成员校验的云函数代理解析：<https://docs.cloudbase.net/api-reference/server/node-sdk/storage>。

菜品卡片、首页最近菜品、菜品详情、制作记录和回收站统一调用 Store 的图片解析接口。解析失败时继续显示现有占位图，不保存空字符串覆盖原始文件 ID；下一次页面同步或下拉刷新会重新尝试。

## 页面行为

- 修改昵称或家庭名称后，本机立即更新并排队上传。
- 其他家人在进入或返回任一页面时静默同步；五秒内快速切页不会重复请求。
- 用户随时可以在页面顶部下拉强制刷新。
- 自动同步失败只更新现有云端状态提示，不弹窗打断。
- 手动刷新失败显示“云端同步失败，请稍后重试”。
- 手动刷新成功不额外弹窗，直接更新页面内容。
- 图片解析失败显示菜名字样占位卡，不展示损坏图片图标。

## 错误与安全边界

- `resolveFiles` 必须先验证家庭成员，再处理文件 ID。
- 空数组直接返回空结果；超过 50 个文件时客户端分批请求。
- 非 `cloud://` 地址由客户端直接使用，不发送到云函数。
- 不属于当前家庭目录的文件 ID 在对应结果项中返回 `FILE_ACCESS_DENIED`，不泄露文件内容。
- 某一个文件校验或解析失败不影响同批其他文件，客户端只使用成功项。
- 云函数失败时保留原始文件 ID，便于后续重试。

## 测试策略

### 合并与迁移

- 家庭名称以较新的 `updatedAt` 为准。
- 成员昵称以较新的 `updatedAt` 为准。
- 时间相同时云端值胜出。
- 缺少 `updatedAt` 的旧数据按 `createdAt` 或 `joinedAt` 迁移。
- `currentMemberId` 在任何云端合并后仍保持本机身份。

### Store 同步

- 并发自动同步只调用一次云端 load。
- 五秒内的非强制同步复用本地状态。
- 强制刷新始终重新拉取。
- 纯远端拉取不执行 save；包含未同步本地变化时才回写。
- 同步失败保留本地状态。

### 图片访问

- 家庭成员可以解析本家庭目录的图片。
- 非成员和跨家庭文件被拒绝。
- 最多处理 50 个去重文件 ID。
- 菜品卡片和详情页使用云函数返回的临时地址。
- 解析失败时保留占位显示并允许下次重试。

### 页面刷新

- 六个页面的 `onShow` 触发静默同步后刷新视图。
- 六个页面的 `onPullDownRefresh` 强制同步。
- 成功和失败路径都调用 `wx.stopPullDownRefresh()`。
- 手动失败显示提示，自动失败不弹窗。

完成后运行全部 Node 测试、烟雾检查、JavaScript 语法检查和 `git diff --check`，并在微信开发者工具中验证两个不同微信账号之间的昵称、家庭名称和图片可见性。

## 部署影响

- 需要重新上传并部署 `family-access` 云函数代码及依赖。
- 不需要新建数据库集合。
- 不需要把云存储调整为全网公开读。
- 小程序代码更新后重新上传体验版进行双账号真机验证。
